# sts-path-generator

A fast TypeScript reimplementation of **Slay the Spire II's act map generator**, plus route analysis and constraint search. It's the engine behind an interactive post on [rio-sanjuan.dev](https://rio-sanjuan.dev).

- **Faithful to the game's rules.** It runs the same five steps as the game's `StandardActMap`: room quotas, 7 non-crossing paths, room types under the placement rules, duplicate-branch pruning with quota repair, and layout. Statistics match maps generated by the game itself (see [Fidelity](#fidelity)).
- **Not seed-exact.** A game seed won't reproduce the in-game map: matching it bit for bit would mean emulating .NET's 64-bit RNG and `HashSet` ordering. Seeds here are this engine's own.
- **Fast.** About 25 µs per map on one core (40k maps/s), with no allocation per map. Route queries take 1–3 µs.

Research notes on how the game's generator works: [research/sts2-map-generation.md](research/sts2-map-generation.md).

## Use

```ts
import { generateMap, mapToString, solveRoute, Room } from 'sts-path-generator';

const map = generateMap('TBL5VNYN4M', { act: 'hive', ascension: 10 });
console.log(mapToString(map));

// The route with the most elites, given at most one before row 6.
const best = solveRoute(map, {
  terms: [{ type: Room.Elite, max: 1, toRow: 5 }],
  score: (type) => (type === Room.Elite ? 1 : 0),
});
```

### Generating

| API | What it does |
|---|---|
| `generateMap(seed, options?, trace?)` | One map. `seed` is a number or a run seed string. |
| `new MapGenerator().generate(config, seed, out?, trace?)` | The batch form: reuse the generator, a resolved config (`resolveConfig(options)`) and an output map. |
| `options.act` / `ascension` / `rooms` | `overgrowth`, `underdocks`, `hive`, `glory`. A1+ deals 8 elites; A10 gives Glory a second boss. |
| `options.rules` | Every rule can be switched: `paths`, `distinctStarts`, `noCrossing`, `quotas: 'sts2' \| 'sts1'`, `noEarlyEliteOrRest`, `noRestBeforeRestRow`, `noRepeats`, `distinctSiblings`, `prune`, `layout`. |
| `options.design` | Hand-drawn `paths` (a column per row) and `pins` (fixed room types). They're carved and typed first, never pruned, and the generator fills in the rest under the real rules. |
| `trace` | Pass an array to record every step (`path`, `assign`, `duplicates`, `remove`, `cut`, `repair`, `move`, …) with a map snapshot at the end of each phase, for animating the build. |

A map is flat typed arrays: `type[cell]`, with edge bitmasks `up[cell]` and `down[cell]`, where `cell = row * 7 + col`. Row 0 holds the start (the Ancient), rows `1..rooms` are the grid, and the boss sits above the top row. `childrenOf`, `parentsOf`, `gridCells`, `roomCounts` and `mapToString` cover the common reads.

### Analyzing routes

Every query is a dynamic program over rows, so none of them enumerate routes.

| API | What it does |
|---|---|
| `countRoutes(map)`, `routesThrough(map)` | Distinct start-to-boss routes, overall and through each node. |
| `countRange(map, term)`, `rangesThrough(map, term)` | Fewest and most rooms of a type on any route, overall and through each node. |
| `solveRoute(map, { terms, score, minimize })` | The best route whose counts meet every term (e.g. "≥2 shops and no elite before row 9"), or `null`. |
| `isRoute(map, cells)` | Validates a route drawn by the user. |

### Finding maps and statistics

| API | What it does |
|---|---|
| `compileConstraints([...])` | A predicate from `someRoute`, `everyRoute`, `rooms`, `routes` and `nodes` constraints, cheapest checks first. |
| `findMaps(config, predicate, { seed, count, limit })` | Seeds of matching maps (regenerate them to draw). |
| `collectStats(config, { seed, count })` / `mergeStats` | Per-cell room-type heatmaps and per-map histograms. |
| `sts-path-generator/worker` | A Web Worker running `find` and `stats` requests (`WorkerRequest`/`WorkerResponse`). Post chunks of seeds to a pool of workers and merge the results. |

## Performance

Apple M5, Node 26, one thread (`npm run bench`):

| | µs/map | maps/s |
|---|---|---|
| Generate (Overgrowth, all steps) | 25 | 40,000 |
| Generate without pruning | 13 | 74,000 |
| Generate with a full trace | 33 | 31,000 |
| `countRoutes` | 0.8 | 1.3M |
| `solveRoute` with two terms | 2.5 | 400,000 |
| Finder (generate + constraint) | 28 | 36,000 |

Tail latency over 100k maps: p50 25 µs, p99 68 µs, p99.9 189 µs.

Pruning is the expensive step. The game lists every route from the start and files every fork-to-merge segment, which in a straightforward port costs ~500 µs per map with a multi-millisecond tail. Here, duplicates are found by walking all branches out of a fork one row at a time, and a partial route survives only if another branch has the same rooms so far on a different node. Almost every route dies within a row or two. Groups are formed row by row and the search stops at the first prune. This makes pruning 20× faster without changing the result: no duplicates remain, and the statistics are unchanged.

## Fidelity

Checked against 201 maps generated by the game's own code (all acts, A0 and A10): node count, starting rooms, edges, route count, and the count of every room type. All agree with this engine's distributions, with every pooled z-score under 1. Neither the game's maps nor 6,000 of ours have a duplicate branch left after pruning. The tests also check every placement rule on thousands of maps, and check the analysis against brute-force route enumeration.
